## Context and Problem Statement

Producers (adapters) and consumers (ingestion, live push, alerts) are deployed independently. The tick message is the contract between them. Without an explicit envelope and versioning rules, a field rename in an adapter silently breaks ingestion. What does a message look like, and how does it evolve?

## Decision Drivers

- D1 — Standard envelope, recognisable to other engineers.
- D2 — Idempotency key and trace context in every message.
- D3 — Schema validated at the boundary ([0010](0010-api-management-ingestion-gateway.md)).
- D4 — Backward-compatible evolution without coordinated deployments.

## Considered Options

1. CloudEvents 1.0 envelope (JSON structured mode) with a versioned JSON Schema for `data`
2. Custom JSON envelope
3. Protocol Buffers with a schema registry

## Decision Outcome

**Chosen option:** Option 1.

### Envelope (v1)

```json
{
  "specversion": "1.0",
  "id": "0192a8f4-6c2e-7b3a-9d41-5f0e8c2a7b19",
  "source": "/adapters/ice-endex",
  "type": "signallog.price.tick.v1",
  "time": "2026-10-18T09:15:02.123Z",
  "dataschema": "https://signallog.example/schemas/price-tick/v1.json",
  "traceparent": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01",
  "data": {
    "instrumentId": "<venueMic>.TFM.2026-12",
    "price": 38.415,
    "currency": "EUR",
    "unit": "MWh",
    "priceType": "LAST",
    "eventTimeUtc": "2026-10-18T09:15:02.000Z",
    "sourceKind": "REPLAY"
  }
}
```

- `id` is a **UUID version 7** generated by the adapter (`Guid.CreateVersion7()`, available since .NET 9; `Guid.NewGuid()`, which produces version 4, is banned for event ids): globally unique, time-ordered, and a valid GUID. It is the Service Bus `MessageId` and the Cosmos DB document id ([0008](0008-data-storage.md)). A GUID is chosen over ULID because Azure tooling that sets message ids (for example APIM's `send-service-bus-message` policy) requires valid GUIDs ([0010](0010-api-management-ingestion-gateway.md)).
- **Identifier representation rule.** Outside process memory, the identifier is always transported and stored as its canonical lowercase string form (`xxxxxxxx-xxxx-7xxx-yxxx-xxxxxxxxxxxx`): in CloudEvents, Service Bus `MessageId`, Cosmos DB `id`, logs and URLs. Binary serialization via `Guid.ToByteArray()` is forbidden, because .NET writes the first three fields little-endian (Windows/COM layout), which differs from the RFC 9562 byte order used by Java, Python, PostgreSQL and Go and breaks the time ordering of UUIDv7. Where bytes are genuinely required (extracting the timestamp, binary interop), use the RFC order explicitly: `ToByteArray(bigEndian: true)`, `TryWriteBytes(span, bigEndian: true, out _)` and `new Guid(bytes, bigEndian: true)` (.NET 8+). Enforced at compile time (see *Enforcement* below).
- `time` is when the adapter produced the event; `data.eventTimeUtc` is the venue's timestamp ([0017](0017-time-and-timezones.md)).
- `traceparent` follows the CloudEvents distributed-tracing extension ([0007](0007-observability.md)).
- Prices are `decimal` in .NET, serialized as JSON numbers; never `double`.
- The instrument identifier format is illustrative; the authoritative format is defined in [0014](0014-instrument-domain-model.md).

### Enforcement (architecture fitness function)

The identifier rules are enforced by the compiler, not by convention, using the Roslyn analyzer package `Microsoft.CodeAnalysis.BannedApiAnalyzers` referenced from `Directory.Build.props` for every project. Entries in the repository-wide `BannedSymbols.txt`:

```text
// ADR 0012 — identifiers
M:System.Guid.ToByteArray;Mixed little-endian layout breaks RFC 9562 byte order and UUIDv7 sorting. Use ToByteArray(bigEndian: true) — ADR 0012
M:System.Guid.NewGuid;Event ids are UUIDv7. Use Guid.CreateVersion7() — ADR 0012
```

- The documentation-comment ID without parentheses (`M:System.Guid.ToByteArray`) matches only the **parameterless** overload; `ToByteArray(bool)` stays allowed.
- Diagnostic `RS0030` is raised to **error** in the root `.editorconfig` (`dotnet_diagnostic.RS0030.severity = error`); by default it is only a warning.
- A justified exception uses `#pragma warning disable RS0030` with a comment referencing this ADR; such suppressions are reviewed in the pull request.
- Limits: the analyzer checks this repository's source only; calls inside third-party libraries and reflection-based calls are not detected.

### Evolution rules

- **Additive changes** (new optional fields) keep the version; consumers ignore unknown fields.
- **Breaking changes** (rename, type change, removal, semantic change) create `v2`: new `type`, new schema, new APIM route (`/v2/ticks`). Both versions are accepted during a migration window; consumers handle both.
- Schemas live in `contracts/` in the repository; contract tests run in CI for every producer and consumer.

### Consequences

- Good, because the envelope is an open standard with .NET SDK support.
- Good, because idempotency and tracing are part of the contract, not an afterthought.
- Bad, because JSON is larger than binary formats; irrelevant at this volume.

### Confirmation

- CI contract tests: every producer's sample output validates against the schema; every consumer passes a test against v1 samples including unknown extra fields.
- Unit test: the timestamp extracted from a generated `id` (RFC byte order) equals the creation time within 1 ms; a build containing a parameterless `Guid.ToByteArray()` or a `Guid.NewGuid()` call fails with `RS0030` (verified by a deliberately failing sample project in CI, or once manually when the rule is introduced).

## Pros and Cons of the Options

### CloudEvents + JSON Schema
- Good, because it is a standard, readable, validated in APIM and has native .NET support.
- Bad, because it is verbose.

### Custom envelope
- Good, because it is minimal.
- Bad, because it reinvents a standard and is harder to explain.

### Protobuf + registry
- Good, because it is compact and strongly typed.
- Bad, because there is no free managed registry here and APIM cannot validate it natively.
