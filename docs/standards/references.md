|---|---|
| Status | Active; applies to a page once it is migrated (section 1) |
| Owner | Solution Architect |

This standard describes **how** pages and code refer to terms, concepts, facts and external sources. The decision **that** every external source is described once in a bibliography and cited by key is recorded in ADR 0021; this page is the operating procedure and changes through a normal pull request.

## 1. Scope and transition

- The standard covers every Markdown page under `docs/`, the repository `README.md`, the Russian mirrors, the C# code, the PowerShell scripts, the workflows and the configuration files that link to the site.
- Pages are migrated story by story (Azure Boards Feature #42 "Citations and references"). `eng/docs/references-legacy.txt` lists the pages that are not migrated yet; they keep their current citations until their story is done. A page leaves the list when its story is done, and no page is added to it.
- A new page follows this standard: the [bibliography](../references/index.md) exists.

## 2. Two kinds of reference

| Kind | Points to | Form | Checked by |
|---|---|---|---|
| Navigation link | A page of the project: a glossary term, a concept, an ADR, a requirement, a standard, a fun fact | Relative Markdown link at the first use on a page | Strict build |
| Citation | An external source that supports a statement | Footnote whose text links to the bibliography entry | Strict build and `check_references.py` |

A navigation link does not replace an explanation. If a term can be explained in a few words, the explanation is written in the text and the link is added for the reader who wants more.

## 3. The bibliography

The bibliography lives in `docs/references/`. The data file `sources.toml` is edited by hand; the page `index.md` is generated by `eng/docs/build_references.py` and is never edited by hand. The page groups the entries by kind and lists for each entry the pages that cite it, so it is regenerated after a citation is added or removed; `build_references.py --check` fails in CI when it is out of date.

### 3.1 Keys

A key is made of lower-case Latin letters, digits and hyphens. A key never changes; when a source moves, only its `url` changes.

| Kind of source | Pattern | Examples |
|---|---|---|
| Work with an author: book, paper, post on the author's blog | `surname-year`, with `-a`, `-b` when two works collide | `nygard-2011`, `ford-2017`, `pope-2008`, `steele-2014` |
| Standard or specification | `body-number` | `rfc-9562`, `iso-8601`, `iso-10383`, `cloudevents-v1-0-2` |
| Living vendor documentation | `vendor-topic` | `ms-cosmos-free-tier`, `gh-rulesets-rules`, `ice-tfm-product` |
| News or press release | `publisher-yyyy-mm-dd-topic` | `ice-2023-01-27-mcm`, `acer-2025-01-31-mcm` |

### 3.2 Entry fields

Field names follow the Citation Style Language (CSL), so the data can be converted for Pandoc or Zotero.

| Field | Required | Holds |
|---|---|---|
| `id` | yes | The key |
| `type` | yes | CSL type: `book`, `article-journal`, `paper-conference`, `report`, `standard`, `legislation`, `webpage`, `post-weblog`, `article-newspaper`, `software` |
| `title` | yes | Title in the language of the source |
| `author` or `publisher` | one of them | Authors, or the organisation |
| `issued` | when known | Date of publication or of the version |
| `version` | for pinned sources | Version, edition or revision |
| `container-title`, `volume`, `issue`, `page` | for articles and papers | Journal or proceedings, volume, issue and pages |
| `doi`, `isbn`, `number` | when they exist | Persistent identifier: DOI, ISBN, RFC number, arXiv identifier with version, article number |
| `url` | for web sources | Address of the page |
| `accessed` | for living sources | Date the source was last checked against the text |
| `archive` | no | Address of a copy in the Web Archive, for a living source whose page may change |
| `tier` | yes | 1 — primary source; 2 — vendor technical documentation; 3 — news, used for dates of events only |
| `stability` | yes | `pinned` — the document does not change; `living` — the page can change |
| `further_reading` | no | `true` when the source supports nothing and is listed for reading only |
| `note` | no | A short remark, for example "first edition, where the term was introduced" |

```toml
[[source]]
id        = "rfc-9562"
type      = "standard"
title     = "Universally Unique IDentifiers (UUIDs)"
author    = ["K. Davis", "B. Peabody", "P. Leach"]
publisher = "IETF"
number    = "RFC 9562"
issued    = "2024-05"
url       = "https://www.rfc-editor.org/rfc/rfc9562"
tier      = 1
stability = "pinned"
```

### 3.3 Tiers

The tier depends on what a source supports, not on where it is published. The blog post in which an author introduced a concept is a primary source for the origin of that concept. Somebody else's summary of the same post is not evidence and can only be further reading. Marketing pages and summary blogs are not evidence.

## 4. Citing in text

```markdown
UUID version 7 starts with a 48-bit Unix timestamp in milliseconds.[^rfc-9562]

[^rfc-9562]: [RFC 9562](../references/index.md#rfc-9562), section 5.7.
```

1. The footnote stands at the end of the passage it supports, after the punctuation. Consecutive sentences from one source get one footnote at the end.
2. The footnote label is the key of the source. When a page cites one source with two locators, the second label gets a suffix: `[^rfc-9562-s6]`. The checker reads the link inside the footnote, not the label.
3. The footnote text holds exactly one link to the bibliography, a short name of the source and a locator (section, page, table or chapter) where the source has one; otherwise a few words on what the source supports. The external URL is not written on the page.
4. Footnote definitions are collected at the end of the Markdown file. The site renders them at the bottom of the page and as tooltips.
5. One statement has at most three sources. When more seem necessary, split the statement or keep the best source.
6. Common knowledge is not cited, and neither is what the linked register already supports, such as the definition of a concept.
7. A number shows its unit (documentation standard, section 2) and, when it comes from outside the project, a footnote.

## 5. Which statements need a citation

| Statement | Form | Example |
|---|---|---|
| Fact about an external product, market or standard: a capability, limit, price, date or recommendation | Footnote | "Service Bus Basic supports queues only" |
| Number taken from an external source | Footnote | "the body of a commit message is wrapped at about 72 characters" |
| Definition of an engineering concept | Link to the concepts register; its sources live there | architectural fitness function |
| Domain term | Link to the glossary | front month |
| Observation made in the project | **Observed** with the date or a link to the pull request | "pull requests #22 to #24 merged without an extra approval" |
| Conclusion of the author | **Inferred** or "author's assessment" | — |
| Decision of the project | Link to the ADR | — |

## 6. Dates

- **The date a source was checked** (`accessed`) lives only in the bibliography. Lines such as "Facts were checked on …" and "(checked …)" are removed from migrated pages.
- **The date on which a fact holds** stays in the text when it is part of the claim: "On 2026-11-06 ICE still listed `TFN` in its product guide."
- Dates are ISO 8601 (documentation standard, section 2).

## 7. Roles of sources

A concept often has several sources that complement each other. The [concepts register](concepts-and-sources.md) lists them by role.

| Role | Meaning | Comparable to |
|---|---|---|
| Origin | Where the concept was introduced | Informative reference (IETF), historical |
| Definition | The current authoritative definition or specification | Normative reference (IETF); `citesAsAuthority` (CiTO) |
| Evidence | Supports a specific fact, number or date | `citesAsEvidence` (CiTO) |
| Method or data | The project uses a method or data from the source | `usesMethodIn`, `usesDataFrom` (CiTO) |
| Further reading | Useful, supports nothing | Informative reference (IETF); `citesAsRecommendedReading` (CiTO) |
| Disputes | Says something else; the text says which source is followed and why | `disagreesWith`, `critiques` (CiTO) |

A story in Fun Facts, an ADR, a requirement and the code that implements a concept are not sources. The register links them next to the sources, so that a reader can follow a concept from its origin to the place where the project uses it.

## 8. Conflicts and confidence

- When sources disagree, both are cited, and the text says which one is followed and why. [ADR 0002](../adr/0002-source-control-platform.md) does this for GitHub Docs and an issue report that contradicts them.
- **Inferred**, **Observed** and **unverified** mark what was not read in a source. A missing fact becomes a row in the page's open questions.

## 9. End of a page

- **See also** — other pages of the project. In ADRs and standards, the **Related** field of the header plays this role.
- **Footnotes** — the sources of the text, rendered by the site.
- **Further reading** — keys of sources that support nothing on the page.

A migrated page has no "Sources" section with full citations. In an ADR, *More Information* keeps links to other decisions and review triggers; external sources move to footnotes.

## 10. Russian mirrors

- A page and its mirror use the same keys and the same anchors; the checker compares them.
- The bibliography is one, in English. Titles of sources stay in their original language.
- The footnote text is translated ("раздел 5.7" for "section 5.7"); the link inside it stays the same.

## 11. Code and configuration

| Refers to | Where | Form | Example |
|---|---|---|---|
| A decision, requirement or business rule | Comments, XML documentation, JSON Schema descriptions, workflows, `.psd1` files | Identifier in text | `ADR 0012`, `NFR-SEC-03`, `BR-PRICE-03` |
| The principle behind a constant or an algorithm | XML documentation | `<seealso href>` to an explicit anchor of the site | `<seealso href="https://alexeygane.github.io/signallog/domain/replay-price-generator/#two-layers"/>` |
| The external source of an algorithm or a number | Comment or `<summary>` next to the code | Key in square brackets | `// SplitMix64 finalizer [steele-2014]` |

- Identifiers keep one spelling: `ADR 0012` in text and code. `ADR-0012` is the tag form on Azure Boards.
- `<seealso href>` points only to an explicit anchor (section 12), never to an anchor generated from a heading such as `#6-two-layers`.
- Code does not hold external URLs: the path is code → documentation → source. Machine identifiers such as `$schema` and `dataschema` are not citations.
- Documentation links to code by file on `main` and the symbol name in backticks, not by line numbers. A historical state is linked by a permanent link with the commit SHA.
- A constant taken from a specification keeps the name the specification uses; its `<summary>` gives the key of the source ([C# coding standard, section 8](coding.md#8-magic-numbers)).

## 12. Anchors

- A section that code, Azure Boards or the cover note links to gets an explicit anchor, `<a id="two-layers"></a>`, on the line before its heading. The anchor is a contract: it is not renamed.
- Glossary terms, concepts, bibliography entries and fun facts have explicit anchors.
- The `{#id}` syntax is not used on listed pages: GitHub shows it as text.
- Links inside `docs/` may use the anchors generated from headings; the strict build checks them.

## 13. Accepted ADRs

Converting the citations of an Accepted ADR to this standard is an editorial change: the decision text does not change, and no superseding ADR is needed. The pull request says "editorial: citations only, no decision text changed", and every other change in it is listed.

## 14. Checks

| Check | Tool | When |
|---|---|---|
| A footnote links to an existing bibliography entry | `zensical build --strict` | Every pull request that changes the documentation |
| The bibliography page matches `sources.toml`; entries are valid | `build_references.py --check` | Every pull request that changes the documentation |
| No unused footnotes; no external URLs outside the bibliography; every entry cited or marked `further_reading`; every concept used; a mirror has the keys of its page | `check_references.py` | Every pull request that changes the documentation |
| Links from code and configuration resolve on the built site; identifiers and keys in code exist | `check_references.py` | Every pull request that changes the documentation, `src/`, `tests/`, `contracts/` or `eng/azure-devops/` |
| External URLs open; living sources were checked within the configured period | Scheduled workflow | Once a week; does not block pull requests |

Pages in the legacy list get warnings instead of errors until they are migrated. `check_references.py` names each finding by kind (`footnote`, `external-url`, `uncited-source`, `unused-concept`, `mirror`, `code-link`, `code-id`, `legacy-list`) with the file and line; links from the project's own site, repository and board are navigation and are not reported as external URLs. A link from code to a site anchor must name an explicit anchor of the source page (section 12).
